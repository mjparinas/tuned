# Updates

Melvin first chose **Google Play in-app updates** (2026-11-17), then **GitHub Releases for now** (2026-11-17, "create github releases for now") so he can install real builds before the app is on Play. Both paths stay in the code; which one a copy uses depends on who installed it.

## GitHub Releases (now)

- `release.yml` runs on every promotion to `main` and by hand. It builds a signed APK and publishes a GitHub release tagged `v<version>` (for example `v1.2.0`), with `tuned.apk` attached. There is no build number in the tag or title (Melvin, 2026-11-17: "get rid of build and just bump major minor patch"); releases before that were tagged `v<version>-build.<run>`, and the updater and `next-version.mjs` still read those. The version name is semver, bumped from the commits since the last release by `scripts/next-version.mjs` (Melvin, 2026-11-17): `feat:` titles bump the minor, everything else the patch, `!` or `BREAKING CHANGE` the major, and `package.json` is a floor for a hand bump. The version code is made from the version, major × 1,000,000 + minor × 1,000 + patch (1.2.3 is 1002003), so each release is newer than the last for Android and the updater, and it is far above the run numbers the old tags used. Minor and patch stay below 1,000. Copies installed from a `-build` release can't read the plain tags, so they need the first plain release installed by hand once.
- A copy that Play didn't install asks GitHub for the latest release (`updates/GitHubUpdates.kt`) each time Tuned comes to the front, at most once an hour, and after each background refresh. Checking only on a cold start missed releases entirely while Tuned stayed open in the background (Melvin, 2026-11-17: "when a new release is up, i dont see it prompt in the app"). When the background refresh finds one, a notification says so. If its version code is higher, the APK downloads in the background, and a small "ready to install" bar appears on the home screen. One tap hands it to Android's installer, which asks to confirm. The first time, Android also asks to allow Tuned to install apps.
- Why it never seemed to work before 1.2.0 (Melvin, 2026-11-17: "the new update is available functionality never works"): up to 1.1.0 Tuned only looked on a cold start, which a phone rarely does, and 1.1.0 couldn't read the plain `v1.2.0` tag, so every one of those updates had to be installed by hand. 1.2.0 is the first copy that finds the next release itself. The check also runs in the app's scope (closing the screen mid-check left Settings stuck on "Checking"), tries again a few minutes after a failed check instead of an hour, resumes a dropped APK download, and throws away a download whose size or SHA-256 doesn't match what GitHub lists. `GitHubUpdatesTest` runs the whole path against GitHub's real answer for this repository.
- **Before a playlist is added too** (Melvin, 2026-11-19: "when the tuned app is opened for the first time and the user hasnt set anything up yet, does it check for a new version"). The check never depended on being signed in, but the Install banner only showed on Home, so a fresh install of an old release downloaded the update and never offered it. The banner (`ui/common/UpdateBanner.kt`) now also sits at the top of the welcome screen.
- Settings › Check for updates asks GitHub straight away, whatever the automatic setting, and says what it found (up to date, couldn't reach GitHub, or ready with an Install button). While the new APK comes down it says so with the size ("Downloading Tuned 2.5.0 · 12 MB of 40 MB") and a spinner.
- **Install shows every step** (Melvin, 2026-11-21: "When I click on install, there should be some type of spinner or an indication that it's downloading, processing, and then it installs. Basically, there needs to be some user feedback so they know that the app didn't just crash or freeze"). The pause he saw was Tuned copying the 40 MB APK into Android's installer on the screen thread before anything changed. Now the copy runs in the app's scope off the screen thread, and the tap at once turns Install into a spinner while the banner (and the Settings row) names the step, numbered as a refresh's are, with a real bar: Step 1 of 3, checking the download (or downloading it again, in MB of the full size, when Android cleared the cache), Step 2 of 3, preparing to install (the copy, as a percentage), Step 3 of 3, opening Android's installer and then waiting for the person to confirm. Cancelling Android's confirm window, or leaving it open and coming back to Tuned, shows Install again with no error. A failure is logged and says what to do with Try again: the download failed (check the connection), not enough space, or the update didn't install. It is one button throughout, Install, spinner, Try again, so a TV remote's focus stays on it. Coming back from allowing Tuned to install apps carries on with the install by itself. `GitHubUpdatesTest` covers the steps, a lost download, a failed one and Try again, and the installer's answers; `UpdateScreenshots` draws each step on a phone and a TV.
- **Install never does nothing on a TV** (Melvin, 2026-11-21, on his Nvidia Shield with Android 11: "when I click install, nothing happens. And when I check the logs, there are nothing in the logs"). Three silent paths, now each said out loud. The remote lands on the Settings › Check for updates row, not the Install button at its end, and OK on the row ran another check that found the same update; with an update waiting, the row itself now installs. When Tuned isn't yet allowed to install apps it opens Android's setting for Tuned, falling back to the list of apps and then security settings because a TV's settings may lack the page; if none opens, or the person comes back without turning it on, Install says what to turn on (on a TV, Security & restrictions › Unknown sources) with Try again. And if Android's installer hasn't answered 30 seconds after the APK is handed over, it says the installer didn't open. Every step of an install (the tap, the device, the permission, the session, the installer's answer) goes in the log under "Updates", so the next report has something to read. `GitHubUpdatesTest` covers no settings page, coming back without the permission, and an installer that never answers.
- Android only installs the update if it is signed with the same key as the installed app, so a swapped download can't replace Tuned. **Keep the upload keystore safe**: without it, installed copies can never update again.
- Settings › Advanced › Check for updates turns this off. Debug builds never check.
- The app needs `REQUEST_INSTALL_PACKAGES` for this. Play doesn't allow that permission, so only the `github` build has it; the `play` build drops it and the updater, and its Settings show no update rows ([premium](premium.md)).
- The bottom of Settings shows the version and, under it, the short commit hash the build came from ("Build 1a2b3c4"), as plain text with no link (Melvin, 2026-11-18: "add the github hash to the bottom of the settings page please. No links"). Release and CI builds pass `GIT_COMMIT` (for a pull request, its own head commit rather than the merge commit GitHub builds); a local build asks git, and a build without git hides the line.

## What's new (Melvin, 2026-11-19)

From Horizon Maps' screenshots, which Melvin wanted Settings to look like. Settings › Tuned › Version has a **What's new** button that opens a sheet for the installed version: a coloured header ("What's new in 1.11.0", with how many changes are new, improved and fixed), then the changes as cards under New, Improved and Fixed pills. The changes are this version's GitHub release notes (`--generate-notes`), read with `ReleaseNotes` (`:core`, tested): `feat` is new, `fix` is fixed, other types improved, and upkeep (dependency bumps, CI, docs, tests, promotions) is left out. The notes are fetched when the sheet opens and not stored; if GitHub can't be reached the sheet says so with Try again.

- It never opens by itself after an update: Tuned has no pop-ups ([AGENTS.md](../../AGENTS.md), "Get out of the way").
- Store builds have no GitHub release to read, so they show the version without the button.
- **On a TV it fills the screen** (Melvin, 2026-11-21: "Dragging handles shouldn't really be on the TV app... what's new should just show the entire set of updates... it should be easy to scroll using the remote"). A bottom sheet opened half way with a drag handle a remote can't use, so a TV shows a full-screen page inside the overscan margin instead: the header and **Done** on the left, always in view, and every change on the right. Each change takes focus with an outline, so Up and Down step through them and the list scrolls; focus starts on the first change (Done while the notes load), Left reaches Done, and Back closes it. Phones and tablets keep the sheet. `WhatsNewTvTest` checks there is no drag handle and the first change has focus.

## Application id (Melvin, 2026-11-19)

The application id and Kotlin package are **`com.tunedplayer.app`** (debug builds `com.tunedplayer.app.debug`), matching the website's domain (Melvin, 2026-11-19: "change the apps package name. should be something like com.tunedplayer.app, change this everywhere"). Releases up to 1.13 were `app.tuned`. It was changed before the first Play upload, because Play fixes an app's id for good once a build is uploaded.

- **Android treats a new id as a different app.** A 1.13 copy's updater still finds the next GitHub release and hands its APK to Android's installer, which installs the new Tuned beside the old one rather than over it. Nothing on the device carries over: open the new app, choose Restore from your Tuned account on the welcome screen (the backup has the playlists, logins, favourites and lists), then uninstall the old app. A copy that never signed in to a Tuned account adds its playlist again.
- **The server accepts both.** `devices/public/.well-known/assetlinks.json` lists both ids with the same signing key, so the TV sign-in link (`/tv`) keeps opening 1.13 copies and opens the new one. Play purchase checks (`devices/lib/play.mjs`) use the new id only, since nothing was ever sold under the old one.
- Stored key names (settings, DataStore files, the database) are unchanged; they live inside each app's own storage, so the rename doesn't touch them.

## Google Play (later)

`release.yml` also builds the `play` App Bundle and uploads it to the Play internal track once `PLAY_SERVICE_ACCOUNT_JSON` exists, with in-app update priority 5. Copies installed from Play ask Play on each start and update straight away (an immediate update), or, where Play allows only a flexible update, download in the background and restart into it. The very first Play upload has to be done by hand in Play Console.

## Signing secrets

- `ANDROID_KEYSTORE_B64`: the upload keystore (alias `upload`), base64.
- `ANDROID_KEYSTORE_PASSWORD`: its password, which is also the key's password.

Until both exist, `release.yml` skips with a notice.
