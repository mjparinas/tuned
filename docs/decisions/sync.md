# Sync between devices

From the app audit, Melvin picked sync between his phone and TV (item 13), and chose "Your Google account (Drive app folder)" over a Tuned server or no cloud at all (2026-11-17), so there's no server of our own to run.

**What syncs** (`BackupRepository.syncCopy`). The saved playlists, every setting a backup holds, favourites and watch later. Which playlist is in use stays each device's own, so the phone and the TV can watch different ones. A device with no playlist in use starts on the first synced one and downloads it. Device-only settings (sync times, the open tab) never sync, as in backups.

**Locked before it leaves.** The copy is sealed with a sync passphrase the person chooses (at least 8 characters, the same on every device) with the backup file's encryption (`core/BackupCrypto`: AES-256-GCM, PBKDF2-SHA256). Google only ever holds ciphertext, and the fingerprint stored beside it is keyed with the passphrase (`core/CloudSync.fingerprint`), so it reveals nothing either. The passphrase is kept sealed with a Keystore key on each device so sync runs without typing; it can't be recovered. A device whose passphrase doesn't match says so in Settings and asks again.

**Google sign-in** (`data/GoogleDrive`). Google's sign-in with a code for TVs and other devices, on phones too: Settings shows a short code and google.com/device, which works the same from a phone or a TV remote, needs no Google Play services, and Tuned never sees the Google password. A button beside the code copies it, as on the Trakt sign-in (Melvin, 2026-11-18). It asks only for `drive.appdata`, a hidden folder in the person's Drive that only Tuned can see. The refresh token is sealed with a Keystore key and stays out of backups; Stop syncing signs out and tells Google to drop it.

**When sign-in fails, say why** (Melvin, 2026-11-18: "Google drive sync doesn't work"). Every failed step used to read "Couldn't reach Google", which hid setup problems on Google's side. Now the dialog names the cause (`core/CloudSync.failure`, with tests) and shows Google's own error under it ("Google said: invalid_client: …"), and the developer log records it: no network, an unknown client ID, a client that isn't the "TVs and Limited Input devices" kind, a wrong client secret, the `drive.appdata` scope refused, access denied (in Testing, only test users can sign in), or the code running out. A Drive API that is turned off in the Cloud project shows as its own status under Sync now rather than as "offline". The keys are trimmed, so a stray space pasted into the GitHub secret can't break sign-in.

**When it runs** (`work/CloudSyncWorker`). When the app opens (to take another device's changes) and when it leaves the screen (to send this one's), once there's a network, retrying later if Drive can't be reached. Settings › Playlists and account › Sync now runs it at once. Nothing on screen waits for it.

**Who wins** (`core/CloudSync.decide`, with tests). The whole copy, newest change wins: if only one device changed, its copy wins; if both did, the later change does. A new device takes what's already in Drive rather than overwriting it. Favourites and watch later are replaced by the winning copy, so removing one on the phone removes it on the TV. Merging item by item is not done yet: two devices changing different settings at the same moment keep only the later device's.

**The app's keys.** Google's "TVs and Limited Input devices" OAuth client comes from the release workflow's secrets `GOOGLE_TV_CLIENT_ID` and `GOOGLE_TV_CLIENT_SECRET` into `BuildConfig`, never committed. A build without them hides sync. Like Trakt's, this kind of client ships its secret in the app by Google's design; it identifies the app, not the person.
