# Diagnostics: crashes, errors and the log

Melvin, 2026-11-17: "optimize for the app not crashing or being unreliable", and for anything unhandled, "a developers mode or debug mode in the settings where I can see the logs, and then I can use that to fix the app."

## What happens to a failure

- **Background work never crashes the app.** `AppContainer.appScope` carries a `CoroutineExceptionHandler` that logs. ViewModels and activities launch fire-and-forget work with `launchSafely(tag) { … }` (`diagnostics/Safely.kt`), which logs a failure and leaves the screen working. Work whose result the person waits for still handles its errors itself and says what went wrong (sign-in, sync, refresh).
- **`attempt(tag, what) { … }`** replaces `runCatching` where the failure is worth knowing about. Unlike `runCatching` it never swallows `CancellationException`, so a cancelled coroutine stops instead of carrying on.
- **Background jobs** (refresh, downloads, channel scans) run inside `logFailures`, so an unexpected failure is logged and ends that run as failed; network failures are still retried as before. A download whose address can't be used is marked failed so the queue moves on.
- **Opening another app** (a trailer, the share sheet, the installer, "allow installs from Tuned") goes through `startActivitySafely`, so a device with nothing to handle it (an Android TV without a browser) logs it instead of crashing.
- **Asking the server for the account's status never throws** (2026-11-20, after Melvin's "on a tv, while the channels were loading, when i went to settings, the app crashed"). A TV opens Settings with its Playlists page beside the list, so the status is asked the moment Settings opens. `AccountRepository.refresh` logs any failure (an address OkHttp can't parse, a refused header, an unexpected error) and keeps the last answer, reads at most 64 KB of the answer, and Settings starts it with `launchSafely` as Home does.
- **Sign-in and sync never stay stuck on "busy"**: whatever fails is logged and the screen says so. A server address OkHttp can't parse says so instead of crashing.
- **Installing an older release over a newer one** starts the database afresh (`fallbackToDestructiveMigrationOnDowngrade`) instead of crashing on every launch; upgrades always migrate.
- **Nothing unhandled crashes the app if it can be kept going** (Melvin, 2026-11-20: "Make it so the app doesn't crash at all. Keep things as stable as possible"; this replaces "a real crash still ends the app"). Every failure nothing else caught is logged and saved as a report (stack trace, device, version and the 200 log lines before it) by `CrashReporter`, and then `CrashPolicy` (`:core`, tested) decides what follows. A coroutine that failed without a handler has already ended and its thread carries on, so the app keeps going and the screen keeps what it last showed; `CoroutineFailureMark`, which kotlinx.coroutines finds through `META-INF/services`, labels those failures so the crash handler can tell them apart. A failure that ends a background thread is left behind the same way. A failure that unwinds the screen thread can't be kept going (nothing would draw or answer taps, the reason a crash used to end the app), so while Tuned is on screen it restarts itself on its home screen instead of freezing or showing Android's "keeps stopping" box. Running out of memory, a screen-thread failure while Tuned isn't on screen, or a second restart within a minute (a crash on every start) still goes to Android as a crash, so a loop ends. Recovered failures save at most one report every 10 seconds. At most 10 reports are kept, on the device only.
- **Freezes leave a report too** (Melvin, 2026-11-19: "Do 1", the freeze catcher from the Horizon Maps review). A freeze, where the screen stops answering and Android offers to close the app, never reaches the crash handler. `FreezeWatch` (`diagnostics/FreezeWatch.kt`) catches it two ways: a low-priority thread asks the screen thread to answer once a second and, after 5 seconds with no answer, saves what the screen thread was doing (once per freeze, `FreezeWatchdog` in `:core`, tested); and on Android 11 and newer, each "not responding" ending Android recorded is saved on the next start with Android's own trace (the first start only remembers where it is, so old ones aren't reported as new). Both are saved beside the crash reports, with the version, device and recent log, and show in Logs. Nothing runs while a debugger has the app paused. A tick of the watchdog that comes more than 3 seconds after the one before means Android paused the whole app (it freezes a cached app's threads in the background), not the screen thread, so the clock starts over rather than reporting a freeze with an idle screen thread (2026-11-21: 2.0.1 to 2.3.0 sent several such reports from Melvin's phone).
- **Every release keeps its R8 mapping** (2026-11-21, after 2.2.0's was lost and a freeze trace from it couldn't be decoded). `release.yml` attaches `tuned-<version>-mapping.txt` to the GitHub release beside `tuned.apk`, and keeps both builds' mappings as the `tuned-r8-mapping` artifact for 90 days (also for bundle-only runs; the two builds run on separate runners and the publish job gathers both). The store build's mapping also goes to Play with each upload. To read a trace, run R8's `retrace` with that release's file.
- **A wrong date says so** (Melvin, 2026-11-19: "Do 2", the wrong-clock hint from the Horizon Maps review). Cheap TV boxes often lose the date when unplugged, and then every secure connection fails as if the server were down. `DeviceClock` (`diagnostics/DeviceClock.kt`) reads the `Date` header of every answer through the shared HTTP client (plain-HTTP playlist servers still answer when HTTPS fails) and `ClockCheck` (`:core`, tested) calls the clock wrong when it is before 1 November 2026 or more than a day from a server's. Then a failed sign-in, the first download's error and Settings › Guide and refresh's last error add: check the date and time in Android's settings. It is logged once.
- **Nothing calls Java that Android 8.0 lacks** (2026-11-21, after Melvin's Shield on Android 11 showed "Couldn't load your channels" and a log full of `NoSuchMethodError: URLEncoder.encode(String, Charset)`). `:core` compiles against a current JDK, whose `URLEncoder`/`URLDecoder` take a `Charset`, but Android only has those from Android 13, so every account and playlist address failed on older phones and TVs. `:core` passes `"UTF-8"` instead, and Animal Sniffer (`:core:animalsnifferMain`, run in CI's lint job) checks `:core`'s code against Android 8.0's Java library (the gummy-bears API 26 signature) and fails on any call it lacks, because Android Lint's NewApi can't see into a plain JVM module. `:app` stays covered by Lint's NewApi.
- **A damaged settings file resets to the defaults** (DataStore `ReplaceFileCorruptionHandler`), and a read error reads as the defaults, instead of crashing every launch.

## The log

- `AppLog` keeps the last 1,000 lines in memory. Every level is always kept (Melvin, 2026-11-18: "remove developer mode but keep logs"); the detailed debug and info lines come only from sync and casting, so they are few, and their text is built lazily. Debug builds mirror every line to logcat.
- **No login ever reaches the log** ([security](security.md)). Every line goes through `AppLog.scrub`: `LogScrubber` (`:core`, tested) masks Xtream stream paths, `user:pass@` addresses and secret query values (`username`, `password`, `token`, `api_key`, …) without knowing the login, and the login in use is masked on top (set by `CredentialStore` on load and save, cleared on sign-out).

## Settings › Updates and advanced › Logs

- **Logs** is always there, under Troubleshooting: Send to Tuned (below), crash reports, then the recent log newest first, with copy, share (plain text, up to 200,000 characters) and clear.
- **Developer mode was removed** (Melvin, 2026-11-18: "remove developer mode but keep logs"). It was a switch that kept the detailed log and showed Logs; now both are always on, so there is nothing to turn on before a problem can be looked into. The old stored `developer_mode` value is simply ignored.

## Report a problem (Melvin, 2026-11-19)

"Do 3", from the Horizon Maps review. Settings › Updates and advanced › Troubleshooting › **Report a problem** asks what happened and, optionally, an email for a reply, then **Send to Tuned** sends it to the admin's Reports ([admin](admin.md)) with everything a fix needs, gathered on its own (`diagnostics/ProblemReport.kt`).

**Wider, no Share instead, and everything goes with it** (Melvin, 2026-11-21: "Can you make this wider? And can you also get rid of the share instead? And ... it should [automatically send the logs], as well as other information, as much as we can, non-identifying information to our server"). So:

- **Nearly the phone's width**: the dialog uses `DialogWideMaxWidth`, so it keeps only the usual 24 dp off each side of a phone and stops at 720 dp on a tablet.
- **Share instead is gone**, and with it the share sheet and the copy to the clipboard. The buttons are Send to Tuned and Cancel.
- **It sends what Logs' Send to Tuned sends**, plus the person's words and email: the whole log (up to 150,000 characters), the last three crash or freeze reports and the device's details (below), through the same `ProblemReport.sendToTuned`. Before, it sent only the last 400 log lines, the latest report and the model.
- **Feedback**: the dialog stays open while it sends, with a spinner and "Sending this log and this device's details…", the fields and buttons locked. A failed send says so in red, keeps what was typed, and turns Send to Tuned into Try again; a sent one closes and the row says "Sent to Tuned".
- **Non-identifying**: the device's details say whether a Tuned account is signed in, never its email (this changes Logs' report too). The email only goes when the person types one for a reply.

## Report from Logs, and none on a TV (Melvin, 2026-11-21)

"on android tv, remove report a problem because people can't type. instead, on the logs screen, there should be a report button and it should automatically send all of the users logs, and all of their device information to me (type of phone, version of os, version of the tuned app, etc. the more data the better). don't forget a spinner while sending". So:

- **Report a problem is gone on a TV**: Troubleshooting there has only Logs. Phones and tablets keep it, with its words.
- **Logs opens on Send to Tuned**, on every device, first in the list and where a TV's remote starts, so OK alone sends it. Nothing to type. A spinner and "Sending this log and this device's details…" while it sends, then "Sent to Tuned" or, in red words, that it couldn't, with the title turned to Try again. The send lives in the screen's view model, so turning the screen doesn't drop it.
- **What goes** (`diagnostics/DeviceDetails.kt`, `ProblemReport.sendLogsToTuned`): the whole log (up to 150,000 characters), the last three crash or freeze reports, and the device's details in sections: Tuned (version, build, GitHub or store, debug, who installed it, when installed and updated, how long it has run, Premium, how many reports are saved); the device (maker, brand, model, device, product, hardware, chip, CPU and cores, TV, tablet or phone, Android and API level, security patch, Android's build and fingerprint, WebView version, touch screen); the screen (pixels, dp, density, font scale, orientation, refresh rate, display modes, HDR); memory (total, free, low, the app's limit and use); storage (free of total, the database, app files, cache, downloads); the network (connected, Wi-Fi, Ethernet, mobile, VPN, whether the internet checked out, metered, speed estimate, private DNS); power (battery, plugged in, battery saver, battery limits); language and time (language, device languages, time zone, 24-hour clock, the time); the account (whether the Tuned account is signed in, never its email; the install id while usage stats are on); and playlists (how many, of which kinds, which is in use, live channels, films, episodes, guide entries, downloads). A fact that can't be read says why rather than stopping the rest.
- **Never a login**: no playlist's server, username, password or link is read into it, only counts and kinds; and the whole text goes through `AppLog.scrub` and then has every saved playlist's password, username, playlist link and guide links masked, as written and as they appear in a link (`DeviceDetailsTest`). The log and crash reports were scrubbed as they were written.
- It goes to the same `POST /api/report` as Report a problem, so it lands in the admin's Reports and its email in the same way ([admin](admin.md)).

## Device smoke test (2026-11-18)

From the gap review Melvin asked for ("what else are we missing"): the app had JVM tests only, so nothing checked the real screens or the one-connection rule end to end. `:smoketest` installs the github debug app on an emulator (a Gradle managed device, Pixel 6, API 34 ATD image) and drives it with UI Automator against `:fakeprovider`, a stand-in provider on the loopback that serves a generated playlist and a 30 second test clip at about the speed it plays, so a stream connection stays open the way a live channel's does. It clears the app's data, adds the playlist link from the welcome screen, waits for the channels, plays one, changes channel twice with the remote's channel key, and goes back to Live TV. It fails if two stream connections were ever open at the same moment. CI runs it on every pull request as **Device smoke test**, part of "CI passed". No real login or playlist is involved. Gradle Managed Devices do not support android-tv images, so Android TV stays covered by Robolectric TV-qualifier tests and a real box ([TV](tv.md)).
