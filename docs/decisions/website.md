The account, TV sign-in, device list and admin pages live on the same site ([accounts](accounts.md), [premium](premium.md), [admin](admin.md)).

**The old GitHub Pages site is gone** (Melvin, 2026-11-20: "i dont think we need this build step anymore", "we have a full website now"). `mjparinas.github.io/tuned` was `docs/index.md` and `docs/privacy.md` published from `main`; `docs/index.md` is deleted and Pages is turned off in the repository's settings, so pushes to `main` no longer build it. `docs/privacy.md` stays as the source of `/privacy`. Every link, including the Google sign-in consent screen's privacy and home page, points at www.tunedplayer.com.

## One header and footer on every page (Melvin, 2026-11-19)

"Every page should have a header and footer, similar to the one on the home page." The header (the channel stack and name, Features, Blog, Account and Download) and the footer (links, the note that Tuned includes no channels, and the store trademarks) are written once, `siteHeader` and `siteFooter` in `lib/site-build.mjs`. The generated pages (landing page and blog) have them inline. The hand-written pages (`/account`, `/tv`, `/devices`, `/check`, `/app/signed-in`) load `site.css` and `web.css` and include `/chrome.js` twice, `<script src="/chrome.js" data-part="header"></script>` first in `<body>` and `data-part="footer"` last, which writes the same header and footer in place before the page draws. `chrome.js` is generated from the same functions, so a change to the header reaches every page. A new page does the same; a test checks the hand-written pages have both. The admin keeps its own look.

## Account pages are wide on a desktop (Melvin, 2026-11-20)

"The width of the account view on the website can be wider please, it's too narrow on desktop." From 960 px wide, a page whose `<main>` has `class="wide"` (`/account`, and any account page that opts in) lines up with the header at 1120 px, and the signed-in cards sit two to a row in page order (`site.css`); a card marked `span` (who is signed in, What Tuned does) takes the whole row. A sign-in card on its own stays at 640 px so it reads easily. Phones and small tablets keep the single 560 px column, unchanged. Cards stay in page order, never rearranged to fill gaps, so the reading and tab order match what you see.

## The blog (Melvin, 2026-11-19)

"Can you add blog posts that talk about whats new for each release and the date", and "ensure that each blog post has a CTA action, link to the android app".

- **Posts are Markdown** with frontmatter (`title`, `description`, `date` as YYYY-MM-DD, `kind`) in `devices/site/posts/`. The file's path is its address: `posts/whats-new/tuned-1-13-0.md` is `/blog/whats-new/tuned-1-13-0/`, and each folder gets its own index page. Kinds: `release` (What's new), `guide`, `compare`, `roundup`; the blog's front page groups posts by kind. The Markdown has headings, lists, tables, links, images, quotes, and lines starting with `<` pass through as HTML; images go in `devices/public/blog/img/`.
- **Every post ends with the call to action** to download Tuned for Android (and the coming-soon stores), from the shared template, so no post adds its own.
- **One post per release.** The releases up to 1.13.0 were written from their GitHub release notes, with a hand-written opening each. From now on `release.yml`, after publishing a GitHub release from `main`, runs `devices/release-post.mjs` on the release's notes (`feat` under New, `perf` under Faster, `fix` under Fixed; CI, tests, docs, refactors and admin-only work left out), rebuilds the site, commits the post to `main` (so it goes live with the release, Pacific date) and merges `main` back into `staging`. An existing post is never overwritten, so a post can be written by hand before the release.
- An RSS feed is at `/blog/feed.xml`.
- **Guides and roundups** (Melvin, 2026-11-19: "add them all", to the list of guides offered for the blog). `posts/guides/` (kind `guide`) has getting started (Xtream, M3U link or file, MAC portal, signing in on a TV with a phone), how-tos (the TV guide, catch-up, recording and downloads, casting, subtitles, profiles), device guides (Android TV, Google TV, Nvidia Shield, tablets), troubleshooting (buffering, an empty guide, the user agent, provider errors), Premium with seats and devices, privacy, and a glossary. `posts/roundups/` (kind `roundup`) has the best IPTV player for Android TV and TiviMate alternatives, which link to every comparison in `posts/vs/`. ## How it's built

No framework and no build step on Vercel, like the rest of `devices/`. The site and server run on Node 26 (Melvin, 2026-11-20, from 22, to match the Vercel project's 26.x setting): `engines` in `devices/package.json` and CI's Node jobs say 26, so Vercel, CI and the tests run the same version. `node devices/build-site.mjs` turns `devices/site/` (`config.mjs`, `features.mjs`, `home.html`, `posts/`) into `devices/public/index.html`, `public/blog/**`, `sitemap.xml`, `blog/feed.xml` and `features.json`, with the shared header, footer, canonical address, Open Graph tags and structured data (`lib/site-build.mjs`). The output is committed; the test `devices/lib/site-build.test.mjs` (CI's Node tests) fails when it is out of date, and Prettier skips the generated pages.

- **`sitemap.xml`** lists the landing page, the blog, each folder's index and every post, on `https://www.tunedplayer.com`. **`robots.txt`** allows everything but `/admin`, `/api/`, `/account`, `/app/`, `/tv` and `/devices`, and names the sitemap.

## Accessibility and standards (Melvin, 2026-11-20)

"Check the website for wcag, accessability, and other web standards." Every page, the account and admin included, meets **WCAG 2.2 AA** in light and dark, and CI keeps it that way.

- **The check** is `node devices/a11y-check.mjs`, run in CI's Formatting job whenever the website changes (about a minute, Chromium cached). It serves `devices/public` as Vercel does and opens every page in light and dark with reduced motion: axe-core's WCAG 2.2 A and AA rules and its best practices, the account page signed out and signed in (a made-up account), and every admin section with `admin-preview.mjs`'s sample data. At 320 px wide no page may scroll sideways (1.4.10), and everything Tab reaches must show a focus ring (2.4.7). Any finding fails CI. A new page is checked without being listed; a page that draws more when a button is pressed (like the admin's sections) has its states added to the check.
- **What the 2026-11-20 audit fixed**: the admin's faint text, violet links and pills, and its green, teal and amber pills were below 4.5:1 and are darker in light and lighter in dark; white on the admin's violet in dark is now 4.5:1. Form fields on the site have an edge of 3:1 against their card (1.4.11) and the same focus ring as buttons, where focus used to show only as a faint border colour. Folder pages of the blog went from h1 straight to h3 (now h2), and comparison tables had an empty heading in their corner; their first column is now row headings, and a table that scrolls sideways can take focus so a keyboard can scroll it. The admin's button columns have a heading a screen reader hears ("Actions"), long names wrap on a phone instead of pushing the admin sideways, and its search box shows focus. Reduced motion turns off every transition on the site. The provider check's dark button text is dark on its light blue.
- **Standards already met, kept**: `lang="en-CA"` on every page, one h1, landmarks (header, nav, main, footer) and a skip link, titles, descriptions, canonical addresses, Open Graph and Twitter cards and structured data on the public pages, `noindex` on the account, TV, device and admin pages, and Prettier-formatted HTML. Pages in `/account`, `/tv` and `/devices` get their headings filled in by script, which validators flag on the raw file; that is expected.
- **Security headers** (`devices/vercel.json`): `Strict-Transport-Security` (two years) and a `Permissions-Policy` that turns off camera, microphone, location, payment and USB were added beside the existing content security policy, `nosniff`, no referrer and no framing.
