# Website

The public website at **www.tunedplayer.com** (Melvin registered it 2026-11-19; until DNS points there it is also `tuned-devices.vercel.app`), served by the Vercel project `tuned-devices` from `devices/public/`. The account, TV sign-in, device list and admin pages live on the same site ([accounts](accounts.md), [premium](premium.md), [admin](admin.md)).

## The landing page (Melvin, 2026-11-19)

"Similar to liftsmith, can you create a beautiful landing page for the app", then "borrow some design from getliftsmith.com" and "add a feature section that lists all of our features". `/` follows Liftsmith's home page: a hero with the app on a phone and the download button (its ticks: free with no ads, phones tablets and Android TV, opens straight to your channels; no version number, Melvin, 2026-11-20: "remove this Version 1.13.0"), a strip of facts, how it works in three steps, the main features each beside real screenshots, **Everything in Tuned** (every feature, grouped), coming soon, questions, the newest blog posts and a closing call to action. It wears the app's look from `site.css` ([branding](branding.md#the-website-melvin-2026-11-19)) plus `web.css`: the channel stack, violet and teal, rounded cards and fully round buttons, light and dark from the device.

- **Screenshots are the app's own screens** drawn with sample data ([screenshots](screenshots.md)), never a real provider, channel or sports brand, saved as WebP in `devices/public/img/`. `img/og.png` is the picture shared links show.
- **The feature list is one file**, `devices/site/features.mjs`, built from this record: a group per area, each feature a title and a line, with `premium: true` on what Premium unlocks. The landing page and `/features.json` (for the account page and anything else that lists features) are built from it. A pull request that adds or removes a feature changes it too.
- **Download** is `/download` on the site, which `vercel.json` redirects to the newest release's APK ([updates](updates.md)). **The site never names GitHub or says the download has everything unlocked** (Melvin, 2026-11-20: "dont mention the github app. remove the website download has everything unlocked"): no GitHub links in the call to action, footer or release posts, release notes that mention GitHub are left out of new posts, and `site-build.test.mjs` fails if a page outside `/blog/vs/` says GitHub.
- **Store badges** (Melvin, 2026-11-19: "similar to lift smith use the proper google play, ios, mac image buttons"; "mention that the samsung tizen app and ios, mac apps are coming soon"): Google Play, App Store, Mac App Store and Samsung TV badges in the stores' standard black style, each dimmed with "Coming soon" until its address is filled in `devices/site/config.mjs` (`stores`), when it becomes a link. No dates are given. As on Liftsmith they are drawn, because the official badge files can't be fetched from where the site is built; swap in the official artwork from Google's and Apple's badge pages when convenient. The iOS, Mac and Samsung TV apps are plans, with nothing built yet.
- Never mention a sleep timer or a second video on screen ([scope](scope.md)); the one-connection rule is a selling point and is stated as such.
- The old order-number page that was at `/` (for someone who lost every Premium device) moved to `/devices`, and the app's Your devices screen points there.

## One header and footer on every page (Melvin, 2026-11-19)

"Every page should have a header and footer, similar to the one on the home page." The header (the channel stack and name, Features, Blog, Account and Download) and the footer (links, the note that Tuned includes no channels, and the store trademarks) are written once, `siteHeader` and `siteFooter` in `lib/site-build.mjs`. The generated pages (landing page and blog) have them inline. The hand-written pages (`/account`, `/tv`, `/devices`, `/check`, `/app/signed-in`) load `site.css` and `web.css` and include `/chrome.js` twice, `<script src="/chrome.js" data-part="header"></script>` first in `<body>` and `data-part="footer"` last, which writes the same header and footer in place before the page draws. `chrome.js` is generated from the same functions, so a change to the header reaches every page. A new page does the same; a test checks the hand-written pages have both. The admin keeps its own look.

## The blog (Melvin, 2026-11-19)

"Can you add blog posts that talk about whats new for each release and the date", and "ensure that each blog post has a CTA action, link to the android app".

- **Posts are Markdown** with frontmatter (`title`, `description`, `date` as YYYY-MM-DD, `kind`) in `devices/site/posts/`. The file's path is its address: `posts/whats-new/tuned-1-13-0.md` is `/blog/whats-new/tuned-1-13-0/`, and each folder gets its own index page. Kinds: `release` (What's new), `guide`, `compare`, `roundup`; the blog's front page groups posts by kind. The Markdown has headings, lists, tables, links, images, quotes, and lines starting with `<` pass through as HTML; images go in `devices/public/blog/img/`.
- **Every post ends with the call to action** to download Tuned for Android (and the coming-soon stores), from the shared template, so no post adds its own.
- **One post per release.** The releases up to 1.13.0 were written from their GitHub release notes, with a hand-written opening each. From now on `release.yml`, after publishing a GitHub release from `main`, runs `devices/release-post.mjs` on the release's notes (`feat` under New, `perf` under Faster, `fix` under Fixed; CI, tests, docs, refactors and admin-only work left out), rebuilds the site, commits the post to `main` (so it goes live with the release, Pacific date) and merges `main` back into `staging`. An existing post is never overwritten, so a post can be written by hand before the release.
- An RSS feed is at `/blog/feed.xml`.
- **Guides and roundups** (Melvin, 2026-11-19: "add them all", to the list of guides offered for the blog). `posts/guides/` (kind `guide`) has getting started (Xtream, M3U link or file, MAC portal, signing in on a TV with a phone), how-tos (the TV guide, catch-up, recording and downloads, casting, subtitles, profiles), device guides (Android TV, Google TV, Nvidia Shield, tablets), troubleshooting (buffering, an empty guide, the user agent, provider errors), Premium with seats and devices, privacy, and a glossary. `posts/roundups/` (kind `roundup`) has the best IPTV player for Android TV and TiviMate alternatives, which link to every comparison in `posts/vs/`. Every claim comes from this record and the app, and their screenshots are the app's own screens with sample data, in `devices/public/blog/img/guides/`. **A pull request that changes a feature, a setting's place or a price these posts describe updates the post too**, as it does this record.
- **Comparisons with the 20 most popular IPTV players** (Melvin, 2026-11-19: "create a new blog post for the top 10 iptv clients and compare and contrast their features to ours, make each post a different page", then "expand that list to the top 20" and "add pricing if possible as well"). One post each in `posts/vs/` (`/blog/vs/tivimate/` and so on): an opening, a table of 16 rows (platforms, playlists, guide, catch-up, recording, live pause, several channels at once, casting, picture-in-picture, downloads, profiles, Trakt, details, subtitles, ads, price), the price in words, where the other app is ahead, where Tuned is ahead, which to pick, and the sources with the date they were checked. They are fair: every claim about another app comes from its developer's own page or store listing (a third-party price guide only where the developer gives none, and said so), anything we couldn't find reads "Not stated by the developer", and Tuned's rows come from these decision files. Multi-view is shown as "No, on purpose", because of the one-connection rule ([scope](scope.md)). When Tuned's features or prices change, update the shared Tuned column and paragraphs in each post; recheck the other apps when a post is more than about six months old.

## How it's built

No framework and no build step on Vercel, like the rest of `devices/`. The site and server run on Node 26 (Melvin, 2026-11-20, from 22, to match the Vercel project's 26.x setting): `engines` in `devices/package.json` and CI's Node jobs say 26, so Vercel, CI and the tests run the same version. `node devices/build-site.mjs` turns `devices/site/` (`config.mjs`, `features.mjs`, `home.html`, `posts/`) into `devices/public/index.html`, `public/blog/**`, `sitemap.xml`, `blog/feed.xml` and `features.json`, with the shared header, footer, canonical address, Open Graph tags and structured data (`lib/site-build.mjs`). The output is committed; the test `devices/lib/site-build.test.mjs` (CI's Node tests) fails when it is out of date, and Prettier skips the generated pages.

- **`sitemap.xml`** lists the landing page, the blog, each folder's index and every post, on `https://www.tunedplayer.com`. **`robots.txt`** allows everything but `/admin`, `/api/`, `/account`, `/app/`, `/tv` and `/devices`, and names the sitemap.
